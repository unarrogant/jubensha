# AI 剧本杀管理与智能主持系统发明报告

## 一、系统总体架构

### 1.1 总体设计

本系统采用“前端交互、后端裁决、智能主持、数据持久化、实时同步”协同工作的架构。剧本内容与游戏引擎相互分离：角色、阶段、地点、线索、推理规则和结局由剧本文件描述，房间管理、阶段推进、权限控制、消息分发和 AI 主持流程由通用服务完成。因此，新增剧本时主要增加内容文件，不需要重新开发游戏流程。

### 1.2 架构组成

系统可以划分为以下六个相互衔接的部分：

1. **客户端接入部分**：使用 Vue 3 构建剧本选择、房间大厅、角色卡、线索、时间线、主持人对话、投票、复盘和管理员页面。客户端通过 REST API 获取数据，通过 WebSocket 接收实时事件，并通过 WebRTC 建立玩家语音连接。
2. **统一网关部分**：由 Nginx 提供页面访问、静态资源服务和反向代理，将 `/api/` 请求转发给 FastAPI，同时转发 WebSocket 升级请求，使普通接口、实时消息和前端页面可以使用同一个访问入口。
3. **游戏服务部分**：由 FastAPI 路由、业务服务和 Repository 组成，负责房间创建与加入、角色分配、阶段倒计时、搜证、推理、线索发放、投票和同伴互评。该部分是游戏规则的最终裁决者。
4. **智能主持部分**：由 DeepSeek 模型和 LangGraph 状态图组成，负责理解玩家提问、判断是否调用工具、生成阶段主持词和整理自然语言回复。AI 不能直接改变房间数据，所有实际操作都必须经过后端工具和权限校验。
5. **数据与通信部分**：Redis 保存实时房间状态和 Agent 会话 checkpoint，MySQL 保存可恢复的完整房间快照；WebSocket 负责公共广播和私密消息，WebRTC 负责玩家之间的音频传输。
6. **部署与运行部分**：使用 Docker Compose 组织前端、后端、Redis 和 MySQL 服务，使用数据卷保存数据库内容，并可以通过 Cloudflare Tunnel 或其他 HTTPS 反向代理提供公网安全访问。

### 1.3 系统运行流程

系统运行时，玩家先在客户端选择剧本并创建或加入房间，后端从 `manifest.json` 读取剧本版本和所需人数。房主开始游戏后，后端验证房主身份和人数，分配唯一角色并初始化第一阶段。

随后，游戏编排服务读取 `stages.json`，按阶段时长推进游戏，并在每次阶段变化时发布主持词、倒计时和可执行操作。玩家的提问通过 WebSocket 进入后端，消息服务保存消息并为当前玩家恢复 Agent 会话；LangGraph 根据阶段、角色、已获得线索和历史记录决定直接回答或调用搜证、推理等工具。

工具执行结果必须经过后端校验，确认阶段权限、玩家身份、线索可见性和去重规则后，才转换为主持人回复。最终状态先写入 Redis 和 MySQL，再通过 WebSocket 广播给对应玩家或整个房间，从而保证多个客户端看到一致的游戏进度。

## 二、核心功能模块

### 2.1 剧本管理模块

剧本管理模块负责剧本发现、版本选择、内容加载和资源访问。每个剧本使用独立目录保存 `manifest.json`、角色、阶段、地点、线索、推理规则、结局、提示词和图片资源。

`ScriptLoader` 扫描剧本目录并选择最高版本，`ScriptBundleLoader` 按 manifest 的文件映射加载完整剧本包。房间创建时固定剧本 ID 和版本，保证游戏过程中不会因为发布新版本而改变当前房间的规则。

### 2.2 房间与角色模块

房间模块提供创建房间、加入房间、查看玩家和开始游戏功能。房间所需人数直接读取剧本的 `player_count`，后端要求实际人数严格等于该值后才允许开始。

角色模块在开始游戏时随机分配唯一角色。其他玩家只能看到昵称和公开角色名称，个人接口才返回当前玩家的秘密、目标、私密背景、时间线和个人线索，从接口层实现角色信息隔离。

### 2.3 阶段与游戏编排模块

阶段模块由 `stages.json` 驱动，支持等待、角色分配、开场、搜证、讨论、投票和结局等阶段。每个阶段包含顺序、持续时间、允许动作、禁止动作和阶段主持要求。

游戏编排服务为每个房间创建独立的异步任务，维护阶段开始时间和截止时间，并在截止后推进下一阶段。投票阶段采用“主持词生成完成后开放投票”的顺序，后端设置 `vote_open` 后才向客户端广播投票事件。

### 2.4 搜证与线索模块

搜证模块将地点分为可调查地点和氛围地点。玩家进入地点后获得自然环境叙述，只有检查正确物品才会获得线索；检查无关物品、错误地点或已经检查过的物品时不会发放线索卡。

线索来源包括阶段开始时的固定发放、地点搜证和符合条件的推理解锁。后端记录已发现的线索 ID，保证同一线索不会被重复发现。线索内容与图片资源由剧本文件配置，玩家只能查看已经发放给自己的线索。

### 2.5 AI 主持模块

AI 主持模块负责玩家私聊和公共阶段播报。玩家提问时，系统向模型提供当前剧本、阶段、玩家角色、可见线索、玩家列表和事件历史；阶段开始或切换时，系统提供阶段配置和游戏状态，让模型生成主持词。

AI 只负责语言理解、工具选择和自然语言表达。房间状态、线索 ID、阶段权限、投票对象和消息可见性均由后端确定，模型不能通过普通文字直接生成真实线索或修改数据。

### 2.6 实时消息与语音模块

实时消息模块负责玩家列表、公共主持词、私聊回复、线索通知、阶段变化、投票更新和结局通知。公共消息广播给房间全部玩家，私密回复只发送给目标玩家。

语音模块使用 WebRTC 点对点音频连接。WebSocket 只承担 Offer、Answer 和 ICE Candidate 转发，浏览器之间直接传输音频。前端还使用 Web Audio API 分析音频能量，在主持人区域显示当前正在发言的玩家角色卡。

### 2.7 投票、复盘与管理员模块

投票模块校验当前阶段、投票对象和重复提交，每名玩家只能投票一次。结局模块统计投票并结合剧本的 `endings.json` 生成完整真相、投票结果、胜负判断和每位角色的最终命运。

同伴互评模块允许玩家选择最佳发言者和最佳推理者，达到规定提交人数后计算并公布结果。管理员模块提供登录、房间监控、房间快照和 Agent 审计查询，可以查看玩家问题、主持人回答、工具调用和互评记录。

## 三、技术实现

### 3.1 前端实现

系统前端采用 Vue 3 和 Vite 构建单页应用，以组件化方式拆分剧本选择、房间大厅、游戏房间、投票复盘和管理员页面。Vue Router 负责页面级路由，Pinia 负责保存当前用户、房间、阶段、消息和线索等共享状态，避免多个页面重复请求或状态不一致。

前端将不同通信职责分开实现：`api.js` 统一封装 REST 请求和错误处理；`websocket.js` 管理实时事件订阅、心跳和断线重连；`webrtc.js` 负责麦克风采集、音频轨道、Offer/Answer 协商、ICE Candidate 交换和远程音频播放。该实现使普通数据请求、实时游戏事件和语音传输互不耦合，降低前端维护成本。

### 3.2 后端实现

后端采用 Python、FastAPI 和 Uvicorn。FastAPI 路由层负责 HTTP/WebSocket 协议转换、身份参数接收和异常响应；Pydantic schema 负责请求参数、工具参数和响应结构校验；领域服务层实现房间、角色、阶段、搜证、消息、投票和复盘规则；Repository 层统一封装 Redis 与 MySQL 的读写。

这种分层方式将“接口协议”“游戏规则”和“数据存储”解耦。例如，开始游戏的接口只负责接收请求，真正的房主身份校验、人数校验和角色分配由服务层完成，数据最终通过 Repository 持久化。因此，替换数据库或增加新的前端入口时，不需要重写核心游戏规则。

### 3.3 LangGraph Agent 实现

AI 主持采用 LangGraph `StateGraph` 编排，使用 Typed State 保存房间 ID、玩家 ID、当前阶段、玩家消息、摘要、工具调用结果和最终回复等结构化状态。模型使用 OpenAI 兼容接口调用 DeepSeek，既可以理解玩家问题，也可以根据当前阶段选择后端工具。

Agent 采用“请求进入、状态整理、模型决策、工具执行、结果校验、语言生成”的顺序处理玩家消息。各节点职责如下：

| 处理节点 | 主要职责 | 输出结果 |
| --- | --- | --- |
| `validate_request` | 校验房间是否存在、玩家是否属于房间、请求类型是否允许，并读取当前阶段和权限信息。 | 合法的请求状态，或明确的拒绝原因。 |
| `compact_history` | 对较早的对话进行摘要，保留已经确认的事实、已获得的线索和最近几轮对话，控制上下文长度。 | 可供模型使用的摘要和近期消息。 |
| `decide` | 调用 DeepSeek，结合剧本规则、玩家角色和当前阶段判断应该直接回答、拒绝回答，还是调用工具。 | 结构化决策，包括回复意图和工具参数。 |
| `tools` | 使用 LangGraph `ToolNode` 执行搜证、推理、线索发放等后端工具。 | 工具执行结果，不直接作为最终消息发送。 |
| `apply_tool_result` | 对工具结果进行二次校验，检查阶段权限、玩家可见性、线索 ID 和重复触发状态。 | 可公开、可私密或不可发送的结构化结果。 |
| `render` | 将模型决策和已校验的工具结果改写成符合主持人口吻的自然语言。 | 最终主持人回复和消息可见范围。 |

该流程可以概括为：

```text
玩家消息
   ↓
请求校验 → 历史压缩 → DeepSeek 决策
                         ↓
                 直接回复 / 调用工具
                         ↓
                    工具结果校验
                         ↓
                    主持人语言生成
                         ↓
              私聊回复或房间公共广播
```

每个房间中的每名玩家使用独立的 Agent thread，checkpoint 通过 RedisSaver 保存。这样可以在多次提问之间恢复会话状态，并通过历史压缩减少重复发送的上下文 Token。模型只负责理解和表达，不能绕过后端规则直接写入房间状态。

### 3.4 实时通信与语音实现

公共消息和私密消息通过 FastAPI WebSocket 连接管理器分发。连接管理器以房间和玩家为维度维护连接，支持向全房间广播阶段变化、主持词和投票状态，也支持只向目标玩家发送私密线索和 AI 回复。

语音部分采用浏览器原生 WebRTC。WebSocket 只负责转发 Offer、Answer 和 ICE Candidate 等信令，音频轨道在玩家浏览器之间传输；在无法建立点对点连接的网络环境中，可以增加 STUN/TURN 服务完成地址发现或中继。该方案避免后端承担全部音频流量，降低服务器带宽压力。

### 3.5 数据持久化实现

系统采用 Redis 与 MySQL 的混合存储。Redis 以 `script-kill:room:<room_id>` 保存实时房间快照，以 RedisSaver 保存 LangGraph checkpoint，满足高频状态读取和会话恢复需求；MySQL 通过 `room_snapshots` 表保存完整 JSON 快照，承担长期持久化和故障恢复职责。

房间状态更新时由 Repository 统一执行双写；读取时优先使用 Redis，Redis 缺失时从 MySQL 恢复。房间销毁时同时删除 Redis 键和 MySQL 快照，避免出现残留房间。该设计兼顾实时访问速度和服务重启后的数据可靠性。

### 3.6 权限控制与一致性实现

系统采用“前端限制 + 后端强校验”的双层控制方式。前端根据用户身份隐藏或禁用无权限按钮，后端在每个接口和 Agent 工具执行前再次校验：开始游戏必须由房主发起且人数严格满足剧本要求；搜证必须处于调查阶段；投票必须处于投票阶段且 `vote_open` 已开启；每名玩家只能提交一次投票；同一线索和推理规则不能重复触发；私密消息不能被广播给其他玩家。

阶段状态、倒计时、投票开关和线索发放均由后端维护，客户端只负责展示。即使用户伪造前端请求，也不能绕过游戏阶段和信息可见性规则，从而保证多人联机时的状态一致性。

### 3.7 容器化与部署实现

系统使用 Docker Compose 编排前端、后端、Redis 和 MySQL。前端镜像在构建阶段执行 Vite 构建，运行阶段由 Nginx 提供静态页面；后端容器运行 Uvicorn；Redis 和 MySQL 使用独立数据卷保存数据。Nginx 同时代理 `/api/`、`/content/` 和 WebSocket 请求，使浏览器只需要访问一个统一入口。

DeepSeek API 密钥、数据库连接地址、Redis 地址和管理员凭据通过环境变量注入，不写入源代码、镜像或 Git 仓库。生产环境可以在 Nginx 外层配置 HTTPS 或 Cloudflare Tunnel，为浏览器麦克风和 WebRTC 提供安全上下文。

### 3.8 技术效果

通过 Vue 3、FastAPI、LangGraph、Redis、MySQL、WebSocket 和 WebRTC 的协同实现，系统获得以下技术效果：

1. 通过剧本 JSON 与通用游戏服务分离，实现多个剧本、多个版本的快速接入。
2. 通过 LangGraph 状态图、工具调用和历史压缩，实现具有会话记忆和规则约束的 AI 主持。
3. 通过后端阶段机、权限校验和事件广播，保证多人联机时的游戏状态一致。
4. 通过 Redis 实时缓存与 MySQL 快照持久化，提高高频访问性能和故障恢复能力。
5. 通过 WebSocket 和 WebRTC，实现跨设备的实时消息、主持播报和玩家语音交流。
